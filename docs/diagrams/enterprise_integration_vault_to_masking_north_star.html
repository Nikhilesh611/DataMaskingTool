Enterprise Integration North Star

How a separately developed service such as HashiCorp Vault is introduced into an enterprise, how different enterprise applications use it, and how our data-masking service can follow the same model.

What we need to prove to the professor:
A third-party service does not need to become part of an enterprise's existing authentication system. The enterprise creates a trust/integration relationship between its identity system and the service. Applications then authenticate to that service using a supported standard mechanism. The service validates the caller and applies its own service-specific policies. This is the model we want to reuse for data masking.

1. The real enterprise problem

Imagine Company A already has its own identity system and many applications:

Company A Users | v Enterprise Identity Provider (Entra / Okta / other) | +------ Application 1 | +------ Application 2 | +------ Application 3 Now Company A installs/uses a separate product: | +------ HashiCorp Vault

Vault does not replace the company's identity provider. Instead, Vault is configured with one or more authentication methods that connect it to identity/workload systems the company already uses.

Vault supports multiple authentication methods because different environments need different ways to identify a client.

HashiCorp Vault — Authentication methods

2. What happens when Vault is introduced?

The important part is the initial setup. The enterprise administrator configures how Vault will trust/authenticate callers.

Enterprise administrator | v Configure Vault | +-- choose authentication method | +-- connect it to existing identity/workload system | +-- configure identity/role mapping | +-- attach Vault policies | v Vault is now ready to accept authenticated clients

So the enterprise is not saying "Vault, trust everyone who has a token." It explicitly configures the identity source and what authenticated identities are allowed to do.

3. Example: Vault using an existing JWT/OIDC identity system

For a JWT/OIDC integration, the existing identity provider remains the issuer of the token.

Enterprise IdP | | issues JWT v Application | | JWT v Vault | | verify signature | check issuer | check audience | check configured claims v Authenticated identity | | map identity/role v Vault policy | v Allowed secret / operation

Vault's JWT/OIDC authentication method supports configuration around the trusted issuer, JWKS/OIDC discovery, audience and claims.

The Vault software is the same product. The identity configuration is different for each deployment.

5. Another clear example: a third-party API in Microsoft Entra

Microsoft Entra shows the same pattern for APIs.

The API is registered as a protected resource. A client application is given permissions to that API. The client obtains an access token from Entra and sends it to the API. The API uses the token's permissions to control access.

Third-party / enterprise API ^ | accepts access tokens for this API | Microsoft Entra ID ^ | issues token with required permissions | Client Application

Microsoft's documentation explicitly describes registering the API, exposing scopes/roles, granting the client permissions, obtaining an access token and having the API authorize based on the token.

6. The standard enterprise pattern we are borrowing

1. Existing enterprise identity system | v 2. Enterprise registers/configures the new service | v 3. Enterprise identity system issues an access token | v 4. Application calls the new service with the token | v 5. New service validates the token | v 6. New service maps identity/permissions to its own policy | v 7. Service performs the requested operation | v 8. Service records an audit event

This is the core model. The exact authentication method can change, but the structure remains.

7. How our masking service uses the same model

Our masking service becomes another protected enterprise service.

ENTERPRISE Existing Identity Provider (Entra / Okta / Keycloak) | | access token v Enterprise App | | token + data v +----------------------+ | MASKING SERVICE | | | | 1. Validate token | | 2. Identify caller | | 3. Map group/role | | 4. Find policy | | 5. Mask data | | 6. Audit | +----------+-----------+ | v Masked data | v Enterprise App

8. How an enterprise would integrate our service

The enterprise should not have to create a new authentication system for us.

Step 1 — Register/configure our API

The enterprise identifies our service as a protected API/resource in its identity platform.

For example, in Entra this means registering the API and defining scopes/roles that client applications can be granted.

Step 2 — Configure which identity system we trust

Our service is configured to trust the enterprise's issuer and to obtain the public keys needed to verify tokens.

For the first implementation, we support OIDC/JWT.

Step 3 — Configure application access

The enterprise gives an application permission to call our masking API.

There are two important cases:

CaseMeaning
Delegated/user accessThe application calls the masking service on behalf of a signed-in user.
Application accessA service calls the masking service as itself.

Microsoft Entra explicitly distinguishes delegated permissions from application permissions. Which one we need depends on whether masking decisions are based on the human user, the calling application, or both.

Microsoft — Application vs delegated permissions

Step 4 — Configure masking identity mapping

We should not assume every enterprise has roles called "analyst" or "auditor".

Instead, our service lets the enterprise map its existing groups/roles to our masking profiles:

Enterprise group Our masking profile finance -> analyst security -> auditor data-admins -> admin

This configuration belongs to our service. The enterprise's IdP remains the source of identity.

Step 5 — Application calls our API

Application | | Authorization: Bearer <access-token> | + sensitive data v Masking Service

The service validates the token before touching the masking operation.

9. Exact runtime flow for our project

User | | already authenticated v Enterprise Application | | gets/has enterprise access token | | POST /mask | Authorization: Bearer <token> | body: sensitive data v Masking Service | +--> Validate signature | +--> Check trusted issuer | +--> Check audience | +--> Check expiry | +--> Read identity/group claims | +--> Map group → masking profile | +--> Load policy | +--> Mask | +--> Audit | v Masked response | v Application | v User

10. Why the token is trustworthy

We do not trust a token because it contains a field saying "role=admin".

We trust it only after cryptographic and configuration checks:

Token | +-- signature valid? +-- issuer is trusted? +-- audience is our service? +-- token is not expired? +-- required claims present? | +-- NO → reject | +-- YES → use identity/permissions

The application cannot simply invent a JWT and have our service accept it.

14. Why this is a credible enterprise architecture

We are not claiming to build an enterprise IAM product.

We are building a separate security service that plugs into an existing enterprise identity system, just as enterprise products such as Vault and protected APIs integrate with existing identity systems. The enterprise controls which applications can call the service; the service validates the identity and applies its own policies.

The important design principle is:

Enterprise owns identity ↓ Our service trusts/validates that identity ↓ Our service owns masking policy ↓ Our service returns only the permitted representation

15. Standardization

We should use existing standards rather than invent a token format:

  • OAuth 2.0 access tokens for API authorization
  • OpenID Connect/OIDC where user identity is involved
  • JWT validation where the IdP issues JWT access tokens
  • OIDC discovery/JWKS for discovering issuer/key information
  • HTTPS/TLS for API communication

OAuth Protected Resource Metadata (RFC 9728) is a current IETF standard for a protected resource to publish information that clients can use to discover authorization-server information.

IETF RFC 9728 — OAuth 2.0 Protected Resource Metadata

16. Final architecture decision

EXISTING ENTERPRISE Identity Provider | | OAuth/OIDC token v Enterprise App | | Bearer token + data v +---------------------+ | OUR MASKING API | +---------------------+ | Token validation | | Identity mapping | | Policy engine | | Masking engine | | Audit | +----------+----------+ | v Masked response

Build this first.

Later, if required, the same masking engine could be placed behind a gateway or data-access proxy so the application never receives raw data. That is an expansion, not a requirement for the first 20-credit implementation.
